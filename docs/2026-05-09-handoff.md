## What's autonomous today

- `/cycle` runs every hour. Pulse reads system state, classifies findings, takes always-allowed auto-fixes, writes to journal/actions/escalations.
- Sync runs hourly. Pulls from origin if behind; refuses on dirty tree.
- Health check runs every 30 min. Validates working-copy discipline (always on `main`, always clean).
- All bots auto-restart if they crash. All bots start on boot.
- Conversation continuity per chat is preserved via `claude --resume` + persisted session map.

## What's still manual today (the gap to close in D2/D3/D4)

- **Pulse → Beacon**: Pulse writes escalations to `pulse-escalations.json`. Nothing reads them automatically. Human reads Pulse's findings and Telegrams Beacon.
- **Beacon ↔ Pulse dialogue**: No inter-agent channel exists. If Beacon needs more info from Pulse, human copy-pastes between Telegram chats.
- **Beacon → Forge**: Human Telegrams Forge after Beacon drafts a spec.
- **PR review dispatch**: No auto-trigger when Forge opens a PR. Human Telegrams Mirror.
- **Mirror → Beacon feedback**: Mirror's verdict goes to the PR; nothing routes it back to Beacon's session.
- **Loop completion → Larry summary**: Beacon doesn't auto-DM Larry when a loop completes.

## Open architectural decisions (carry into next session)

### 1. Approval gate (Larry's design call, 2026-05-09)

In Phase D3, Beacon's flow becomes:

> Pulse dispatches → Beacon analyzes & drafts plan → **Beacon DMs Larry via Telegram with the plan, asks for approve/modify/reject** → on `approved`, Beacon dispatches to Forge → Forge implements → Mirror reviews → Beacon DMs Larry summary.

The approval gate is the safety rail that keeps the system in "Medium autonomy" (proposed-then-confirmed). It can be widened later with carve-outs (auto-approve for `[blue]` Pulse findings on isolated `~/agent-core/scripts/` changes < 50 lines), but the **default is always: ask Larry before dispatching to Forge**.

Implementation (D3):
- Beacon's bot needs to recognize Larry's reply ("approved" / "yes" / "go" / "no" / specific modifications) and route the response back into her session
- An approval-pending state must persist across bot restarts (in `~/agents/state/beacon-pending-approvals.json`)
- Approval timeout: if no reply within N hours (default: 24h), Beacon does nothing, journals the timeout, dispatches no work

### 2. Ledger agent (Larry's design call, 2026-05-09; Phase F+)

8th agent, codename **Ledger**. Role: Accountant/CFO. Watches all agent costs and cloud bills, keeps ledgers, flags anomalies, dispatches optimization specs through the normal pipeline.

**Why deferred to Phase F+:**
- Needs spend data history to be useful (today we have ~5 cycles' data, not enough)
- Cost surface keeps growing (Aide in Phase E, Mini Brains adds Vercel+Supabase in Phase F, etc.) — building Ledger before the surface stabilizes means rebuilding her checks every phase

**What we should do now (in D2):** start *capturing* cost data so when Ledger arrives there's a year's history to analyze. Add a small "cost capture" hook to `run_cycle.sh` (and later to the agent inbox watchers) that appends a JSON line to `~/agents/blackboard/costs.jsonl` after every Claude Code invocation:

```json
{"ts":"<ISO>","agent":"pulse","task":"cycle-iter-N","model":"claude-sonnet-4-6","input_tokens":N,"output_tokens":N,"cache_read":N,"cache_creation":N,"cost_usd":0.84,"source":"cycle.last-output.json"}
```

The data is already in `cycle.last-output.json` (the `total_cost_usd` field, the `usage` block, the `modelUsage` block). Just needs extraction. ~30 min of work.

**Ledger's eventual scope:**
- Read `costs.jsonl` (rolled up into daily/weekly summaries)
- Read DigitalOcean billing via `doctl` (when implemented)
- Read Anthropic API usage (requires the dedicated billing-scope API key, deferred since first cycles use Claude Code OAuth)
- Read Vercel + Supabase costs once Mini Brains is deployed
- Weekly summary DM to Larry with totals, trends, anomalies
- Continuous optimization scan, dispatches fixes through Beacon → Forge → Mirror

**Ledger's authority:** cannot spend money, cannot touch credentials, cannot change billing settings. Read + journal + dispatch optimization tasks only.

## Phase D2/D3/D4 spec (next 2–3 sessions)

### D2 — Inbox watchers + Pulse→Beacon dispatch + cost capture (~3 hr)

1. **Build a per-agent inbox watcher daemon.** Polls `~/agents/inboxes/<agent>/` for new HANDSHAKE-conformant JSON tasks. When a task arrives:
   - Validate via `dispatch_validator.py`
   - Claim via `dispatch_lease.py` (so two watchers don't double-pick)
   - Invoke `claude --print --resume <session-from-task>` in the agent's CWD with the task's `prompt` as the input
   - Write result to `outboxes/<agent>/<task-id>.json`
   - Archive consumed task to `inboxes/<agent>/.archive/`
   - Log to `~/agents/logs/<agent>_inbox_watcher.log`

   Implementation choice: one watcher per agent (4 systemd units) OR one shared watcher process with a `--agent <name>` flag. I'd lean **one shared watcher** (less systemd unit duplication) but it needs to spawn parallel Claude Code processes per agent.

2. **Update `cycle-prompt.md` so Pulse dispatches to Beacon's inbox.** Currently Pulse writes to `pulse-escalations.json` only. Add a new section:
   > "For each escalation classified as `[red]` or `[yellow]` with a clear systemic fix candidate, also write a HANDSHAKE-conformant task to `~/agents/inboxes/beacon/cycle-finding-<slug>.json` with `prompt: 'Read pulse-escalations.json entry <iter>:<idx>, draft a fix plan, then DM Larry for approval per D3 protocol.'` Tag with `dedup_identity: 'cycle-finding:<canonical-slug>'`."

3. **Cost capture hook.** Modify `run_cycle.sh` to extract cost data from `cycle.last-output.json` and append to `~/agents/blackboard/costs.jsonl`. Same for any future agent invocations that produce a `last-output.json`-style record.

4. **Test end-to-end:** kick a manual `/cycle` that produces a `[yellow]` escalation, verify the JSON task lands in Beacon's inbox, verify the watcher picks it up and invokes Beacon, verify Beacon writes a result to her outbox.

### D3 — Beacon ↔ Pulse dialogue + Beacon → Forge dispatch + approval gate (~3–4 hr)

5. **Beacon ↔ Pulse dialogue.** When Beacon needs clarification, she writes to `~/agents/inboxes/pulse/clarify-<slug>.json`. Pulse's watcher invokes Pulse, who reads the question, formulates a one-shot answer (no full cycle), writes result to `outboxes/pulse/`. Beacon's watcher detects the matching outbox file via dedup_identity correlation and resumes Beacon's task with the new context.

6. **Approval gate (Larry's call):**
   - When Beacon completes her plan, she writes a Telegram DM to Larry (via her bot's outgoing message API, not via inbox)
   - Format: `🪔 Plan ready for <slug>. Spec attached. Reply 'approve', 'modify <X>', or 'reject'. Times out 24h.`
   - Beacon's bot recognizes Larry's reply, routes back into Beacon's session
   - On `approve`: Beacon writes task to `inboxes/forge/`
   - On `modify X`: Beacon revises plan, re-DMs Larry
   - On `reject` or timeout: Beacon does nothing, journals the outcome

7. **Beacon → Forge dispatch.** Beacon writes the spec file to `agents/beacon/specs/<slug>.md` and a task to `inboxes/forge/spec-<slug>.json` referencing the spec. Forge's watcher picks it up, Forge implements per her Build Loop, opens PR.

### D4 — PR-aware Mirror dispatch + Beacon → Larry summary (~2–3 hr)

8. **Mirror dispatch on PR open.** Two options:
   - (a) Forge's task includes a final step: "after PR opens, write task to `inboxes/mirror/review-pr-<num>.json`"
   - (b) Pulse's PR-state check (already in Health Check Suite) detects new PRs and dispatches to Mirror
   - Lean: (a) — tighter loop, no dependency on cycle cadence

9. **Mirror feedback to Beacon.** Mirror's review verdict (`approve` / `request-changes` / `hold-for-clarification`) gets written to `outboxes/mirror/`. If `approve`, the loop proceeds to merge. If `request-changes`, Mirror writes a task back to `inboxes/forge/` for iteration. If `hold-for-clarification`, task to `inboxes/beacon/` for spec update.

10. **Beacon → Larry completion summary.** When the loop closes (PR merged, post-merge verifier green), Beacon detects completion via outbox/blackboard signal and DMs Larry: `🪔 Done. <slug> shipped in PR #<N>. <one-line summary of what changed>. Cycle: Pulse caught X → spec → Forge → Mirror approved at <ts> → merged at <ts>.`

After D4, the loop you described in our last conversation runs end-to-end autonomously, gated only by your approval at step 6.

## Operational gotchas & landmines (read before debugging)

### Claude Code permissions (settings.json)

We hit this twice today. Notes:

- `~/.claude/settings.json` is the user-wide permissions file. It overrides Claude Code's default deny.
- The glob `Read(/home/larry/agent-core/**)` — **didn't work** with this Claude Code version. Adding `Read(*)` as a catch-all unblocked things. We have many redundant patterns in the allowlist now; can be trimmed once we know exactly which one matches.
- Writes need explicit allowlisting too. We added `Edit(*)` and `Write(*)` (with explicit `Read(/home/larry/credentials/**)` deny so secrets are still protected).
- For Bash tools, claude-code uses pattern `Bash(<command>:*)` (e.g., `Bash(git fetch:*)`). The `:*` matches any args.
- **Currently denied by policy**: `Bash(rm -rf:*)`, `Bash(sudo rm:*)`, `Bash(git push --force:*)`, `Bash(git reset --hard:*)`, `Read(/home/larry/credentials/**)`, `Read(/etc/**)`, `Read(/home/larry/.claude/.credentials.json)`.

### systemd ReadWritePaths

Don't reference paths that don't exist. We had `/home/larry/.config/anthropic` (doesn't exist; Claude Code uses `/home/larry/.claude`) — caused all 4 bots + cycle to fail with `status=226/NAMESPACE` until fixed. Verify any new path with `ls -la` before adding to `ReadWritePaths=`.

### Cycle cost reality

- First iter on Opus 4.7 (1M-context): **$2.33** for 6m47s
- Second iter on Sonnet 4.6: **$0.84** for 5m35s — that's the right baseline
- At 1h cadence: ~$600/mo. At 30-min: ~$1,200/mo. At 4h: ~$150/mo.
- Tune up only if Pulse misses something real. Default direction is *down*, not up.

### Bot session-resume retry pattern (open issue, watch-listed by Pulse)

All 4 bots exhibit on cold-start first message: `claude exit 1: No conversation found with session ID: <uuid>` → bot retries without `--resume` → success. Costs one extra subprocess per first message. Pulse identified this in iter 1. Will be the natural first Build Loop test in D3 — Pulse → Beacon (D2 wiring) → spec → Forge implements fix → Mirror reviews → merge. The fix likely lives in `scripts/agent_telegram_bot.py` (and `scripts/beacon_telegram_bot.py`): detect `session ID not found` error specifically and clear the session map entry rather than just retrying without `--resume`.

### Beacon log-silence false positive (open issue, calibrated by Pulse)

Pulse's Check C threshold (>30m log silence → ask-then-do) fires on idle Telegram polling periods. The bot logs nothing when no user messages arrive. Need either a "messages-received" signal or a longer threshold (or signal-based: if process is alive AND no errors AND inbox is empty, idle is fine). Not urgent — Pulse already noted this as a calibration issue in `agents/pulse/MEMORY.md`.

### agent_runner.py is partially adapted (Phase D wiring concern)

`scripts/agent_runner.py` (1144 lines) was adapted by a subagent during Phase C/D pre-staging but has three known issues that bite if it's invoked without `working_dir` override:
- Line 501 default `cwd = ~/agents/agents/<id>/workspace/` (doesn't match Larry's layout)
- Line 694 `repo_dir = ~/agents/agents/<id>/workspace/repo`
- Line 936 `SWEEP_LEDGERS_DIR = ~/agents/shared/sweep-ledgers/` (we dropped sweep-ledgers entirely)

For D2 inbox watchers, we have two paths: (a) write a thin watcher that bypasses agent_runner.py entirely and just invokes `claude --print` directly per-agent, or (b) fix the three issues in agent_runner.py and use it as the canonical agent-spawning mechanism. Lean: **(a) — write a thin watcher**. agent_runner.py's complexity is GM-specific orchestration we don't need yet.

### Working-copy discipline (`gm-agent-core` health check)

Working tree on the droplet must be clean and on `main`. The `agent_core_health_check.py` runs every 30 min and would alert (or, with notify_larry.py wired, DM Larry) on violation. After any commit done from the droplet (including Pulse's auto-commits of journal/MEMORY entries), make sure tree returns clean.

When Pulse writes the journal during a cycle, the tree becomes dirty. Currently a human commits + pushes those changes (we did this manually for iter 1). **In D2 we should add an auto-commit step to `run_cycle.sh`** so the tree returns clean after every cycle:

```bash
# after the claude invocation succeeds:
if ! git -C "$HOME/agent-core" diff --quiet; then
  cd "$HOME/agent-core"
  git add runbooks/cycle-journal.md runbooks/cycle-actions.jsonl agents/pulse/MEMORY.md agents/pulse/memory/ 2>/dev/null
  git commit -q -m "Pulse cycle iter $(date '+%Y%m%d-%H%M%S')" || true
  git push -q origin main || true
fi
```
