# Rotate Supabase database password

> **DESTRUCTIVE OPERATION — read all six steps before starting.** Resetting the database password invalidates the prior value the instant the new one is shown by Supabase. Every existing connection that holds the old password — including the droplet's `supabase` CLI link state, any psql sessions, and the data-plane `supabase-py` clients — drops on next request. You must re-run `supabase link` in step 6 before the CLI works again. The data-plane JWTs (`SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) are NOT affected — those go through the REST gateway and don't carry the DB password.

**When to run this:** only on suspected compromise of `SUPABASE_DB_PASSWORD`. There is no scheduled cadence (`rotation_type: revocation_only`).

**Severity if lapsed:** high. The droplet's `supabase` CLI workflow (`supabase link`, `supabase db push`) breaks; direct psql tooling breaks. Migrations can be applied from Larry's Mac CLI as a fallback once the new password is also installed in 1Password.

**Time required:** ~15 minutes wall-clock (longer than the access-token rotation because of the re-link step).

**Special note — dual storage:** `SUPABASE_DB_PASSWORD` lives in BOTH `/home/larry/credentials/.env.larry` on the droplet AND a 1Password entry on Larry's Mac. Both copies must be updated in the same rotation window, or the next time Larry needs the password from 1Password it will be wrong.

## Steps

### 1. Regenerate the database password

1. Open https://supabase.com/dashboard/project/ezldtkbhexyrgujqmxpd/settings/database in a browser logged in as `agent.beacon.ourliberty@gmail.com`.
2. Scroll to **Database Password** → click **Reset database password**.
3. Confirm the destructive warning dialog. Supabase generates a new password (alphanumeric + symbols, ~24 chars).
4. **Copy the new password immediately.** Supabase shows it exactly once. If you navigate away you must reset again.
5. Best practice: paste it into your laptop's 1Password entry first (as the new value, keeping the old one annotated as "previous — rotated YYYY-MM-DD"), THEN re-copy from 1Password before running step 2. That guarantees the 1Password copy is captured even if step 2 fails.

### 2. Install on the droplet

From your laptop's Terminal, with the new password on your clipboard:

```bash
pbpaste | ssh larry@134.209.44.80 'python3 -c "
import sys, re, os, tempfile
p = \"/home/larry/credentials/.env.larry\"
pw = sys.stdin.read().strip()
assert pw and len(pw) >= 12 and \" \" not in pw and \"\n\" not in pw, \"db-password validation failed\"
content = open(p).read()
new, n = re.subn(r\"^SUPABASE_DB_PASSWORD=.*$\", f\"SUPABASE_DB_PASSWORD='\''{pw}'\''\", content, flags=re.M)
assert n == 1, f\"expected 1 replacement, got {n}\"
fd, tmp = tempfile.mkstemp(dir=os.path.dirname(p))
os.write(fd, new.encode()); os.close(fd); os.chmod(tmp, 0o600); os.rename(tmp, p)
print(f\"OK: SUPABASE_DB_PASSWORD updated ({len(pw)} chars)\")"'
```

Then clear your clipboard:

```bash
pbcopy < /dev/null
```

The value is single-quoted on disk (codified item #57): `SUPABASE_DB_PASSWORD='...'`. The DB password generated by Supabase frequently contains shell-special chars (`$`, `!`, `&`); without single-quotes, `source` mis-parses the value.

### 3. Verify the new password works (via re-link in step 6)

There is no useful standalone verify step BEFORE the re-link — the existing `~/ourliberty-dashboard/.supabase/` link state was authenticated with the OLD password and is already invalid. The first opportunity to confirm the new password is the `supabase link` invocation in step 6, which prompts for the DB password (read from `SUPABASE_DB_PASSWORD` via env) and stores the new link state.

If you want an independent check before re-linking, run a one-shot psql round-trip:

```bash
ssh larry@134.209.44.80 'set -a && source /home/larry/credentials/.env.larry && set +a && \
  PGPASSWORD="$SUPABASE_DB_PASSWORD" psql \
    "postgresql://postgres@db.ezldtkbhexyrgujqmxpd.supabase.co:5432/postgres" \
    -c "select 1 as ok"'
```

Expected output: `ok` column with value `1`. If you see `password authentication failed`, the install didn't take — repeat step 2 with a fresh copy from 1Password.

### 4. Revoke is implicit

There is no separate revoke step. Supabase's reset invalidates the old password atomically when the new one is generated in step 1. Any connection still holding the old password is already dead by the time you finish step 1.

### 5. Update the registry

Edit `config/token-rotation-schedule.json`:

- `last_rotated_at` → today's date (`YYYY-MM-DD`)
- `next_rotation_due` stays `null` (rotation_type is `revocation_only` — there is no scheduled next rotation)
- `calendar_event_url` stays `null` (no scheduled reminder; rotation only happens on compromise)

Open a PR titled `chore(creds): rotate Supabase DB password <YYYY-MM-DD>` — the discipline expects the registry stays in sync with reality.

### 6. Re-link the project (post-rotation)

The droplet's `~/ourliberty-dashboard/.supabase/` link state was authenticated with the OLD password and is now invalid. Re-run `supabase link` with both `SUPABASE_ACCESS_TOKEN` and the new `SUPABASE_DB_PASSWORD` in env:

```bash
ssh larry@134.209.44.80 'set -a && source /home/larry/credentials/.env.larry && set +a && \
  cd ~/ourliberty-dashboard && \
  PATH=~/.local/share/supabase:$PATH supabase link --project-ref ezldtkbhexyrgujqmxpd'
```

Expected output: `Finished supabase link.` Confirm with:

```bash
ssh larry@134.209.44.80 'cd ~/ourliberty-dashboard && \
  PATH=~/.local/share/supabase:$PATH supabase migration list --linked'
```

Expected: the migration table prints without errors and shows the current applied migrations.

**Final sync — update 1Password.** If you didn't already capture the new password to 1Password in step 1, do it now. The 1Password entry is `Supabase — ourliberty-pm-dashboard DB password`. Annotate the prior value as "previous — rotated YYYY-MM-DD" so future-you knows it's intentionally archived.

## Rollback

If something goes wrong:

1. **Rotation went bad before step 6** — the old password is already invalidated; there is no rollback to the prior value. Re-reset in the Supabase dashboard to generate ANOTHER new password and repeat from step 2.
2. **Re-link in step 6 fails** — verify env: `ssh larry@134.209.44.80 'set -a && source /home/larry/credentials/.env.larry && set +a && echo "ACCESS=${SUPABASE_ACCESS_TOKEN:0:8}... DB_LEN=${#SUPABASE_DB_PASSWORD}"'`. Confirm `SUPABASE_ACCESS_TOKEN` starts with `sbp_` and `SUPABASE_DB_PASSWORD` length matches what you pasted. If env is right but `supabase link` still fails on auth, the password install in step 2 may have shell-quoting drift — re-paste from 1Password.
3. **The 1Password copy and droplet copy diverge** — the droplet copy is the working source of truth (the system reads from `.env.larry`). Re-sync 1Password to match the droplet by SSHing in and reading the value: `ssh larry@134.209.44.80 'grep ^SUPABASE_DB_PASSWORD= /home/larry/credentials/.env.larry'`.

The destructive window is step 1 itself — there is no pre-step rollback. Have the install + re-link commands pre-typed in your terminal so the gap between reset and re-link is seconds, not minutes.
