## ROUTING CONSTRAINT (discovered iter 36)

Pulse can only dispatch to Beacon — HARD_TOPOLOGY in `routing_validator.py` line 54 restricts `'pulse': {'beacon'}`. Pulse→Forge is explicitly blocked at the validator layer. Any cycle-fix permanent-fix dispatch MUST go to Beacon (who then relays to Forge). cycle-prompt.md routing rules (Section G, "code shape → Forge") are accurate in spirit but Pulse must send to Beacon, not Forge directly.

**Exception: Pulse as approval gate for its own dispatches (discovered post-iter-440 notification).** For Pulse-originated Beacon tasks, the outbox notifier routes APPROVAL_REQUESTs back to Pulse at `depth=1` rather than queuing for Larry's approval or auto-approving. `pending-approvals.json` stays at 0. In this case Pulse IS the approval gate and must dispatch directly to Forge using `safe_write_inbox(target_agent='forge', source_agent='beacon', ...)`. The `source: 'beacon'` is correct because Beacon produced the spec — Pulse is approving on Beacon's behalf. This is the `dispatch_approved()` equivalent for the Pulse-gate path.

The symptom is: Beacon archive has the dispatch file + Forge archive has no corresponding build brief. The false "in pipeline" signal comes from MEMORY/journal noting "Beacon processed dispatch" when only the *input* was consumed, not the *output* written. **Diagnosis rule:** confirm pipeline health by checking BOTH beacon/.archive (dispatch consumed) AND forge/.archive (build brief consumed) — both must exist. **Pattern watch:** if Beacon archive has a dispatch but Forge has no brief within 30 min, flag as potential OAuth-blocked session. At 3/3 occurrences → dispatch to Beacon to spec "session resumption on OAuth restore."

- **cycle.timer SubState=running → NEXT=`-` in list-timers (iter 478).** When ourliberty-cycle.service is executing, the timer is in "running" state and list-timers shows NEXT=`-`. This is a display artifact, not an infinity trap. The `TimersCalendar` property shows `OnCalendar=*-*-* *:00/5:00` (OnCalendar, not OnUnitActiveSec). Once the service exits, the timer recomputes NEXT normally. Use `systemctl show ourliberty-cycle.timer --property=TimersCalendar,SubState` to distinguish in-progress (running) from stuck (waiting + n/a in NEXT).

- **Monotonic timers: `NextElapseUSecRealtime=` empty ≠ infinity trap (iter 477).** `ourliberty-heal-stale-daemon-code.timer` (OnUnitActiveSec) shows empty `NextElapseUSecRealtime` but IS active with valid next-fire time visible in `systemctl list-timers`. The infinity trap manifests as `n/a` in the NEXT column of `list-timers`, not as an empty RealTime property. **Check 5 diagnosis rule:** use `list-timers` to confirm NEXT column has a real time; `NextElapseUSecRealtime=` is insufficient for monotonic timers.
