## 1. Problem statement

E4.0 stood up an empty Supabase project. E4.1 fills it with the v1 schema for the PM data model defined in the overview spec § 5.1 — five tables (`programs`, `projects`, `tasks`, `events`, `decisions`) backing the unified PM dashboard. After this ships, the Supabase project has a queryable structure that E4.2's migration script can populate with the Marvin Mission Control data, and E4.3's `pm_writer` library can use as the persistence layer for agent OS dispatches.

Ships zero application logic — no API routes, no UI changes, no agent integration. Pure data layer + migrations harness + CI gate.

**Trigger:** E4.0 fully closed (PR #84 calibration merged + smoke tests pass).

### 4.3 New file: `supabase/migrations/0001_initial_pm_schema.sql`

The big one. Self-contained SQL migration. Content (Forge implements; this is the contract):

```sql
-- 0001_initial_pm_schema.sql — Phase E4.1 — Programs/Projects/Tasks/Events/Decisions
-- Idempotent NOT required (migrations run once); transactional (supabase db push wraps in txn).

-- ============================================================
-- Programs (top-level grouping)
-- ============================================================
CREATE TABLE programs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL UNIQUE,
  description TEXT,
  color TEXT,  -- hex like '#6366F1' for UI grouping; null = default
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'archived')),
  position INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- ============================================================
-- Projects (under Programs)
-- ============================================================
CREATE TABLE projects (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  program_id UUID NOT NULL REFERENCES programs(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  description TEXT,
  reporting_brief TEXT,
  owner TEXT,
  status TEXT NOT NULL DEFAULT 'notstarted' CHECK (status IN ('notstarted', 'inprogress', 'done', 'blocked', 'dropped')),
  priority TEXT NOT NULL DEFAULT 'medium' CHECK (priority IN ('high', 'medium', 'low')),
  blocker_type TEXT,
  blocker_note TEXT,
  next_action TEXT,
  why_it_matters TEXT,
  links JSONB NOT NULL DEFAULT '[]'::jsonb,
  project_type TEXT NOT NULL DEFAULT 'personal' CHECK (project_type IN ('personal', 'agent_os_build', 'client', 'research')),
  started_at TIMESTAMPTZ,
  last_updated TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  position INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX projects_program_id_idx ON projects(program_id);
CREATE INDEX projects_status_idx ON projects(status);

-- ============================================================
-- Tasks (under Projects; both human + agent_dispatch)
-- ============================================================
CREATE TABLE tasks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  external_id TEXT,  -- e.g. "task-30-canonical-repo-paths-to-config" for agent dispatches
  agent TEXT,        -- 'forge' | 'mirror' | 'beacon' | 'pulse' | NULL for human tasks
  name TEXT NOT NULL,
  description TEXT,
  task_type TEXT NOT NULL DEFAULT 'human' CHECK (task_type IN ('human', 'agent_dispatch')),
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'in_progress', 'blocked', 'completed', 'cancelled')),
  assignee TEXT,
  due_date DATE,
  pr_url TEXT,
  spec_path TEXT,
  cost_usd NUMERIC(10, 4),
  duration_seconds INTEGER,
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  position INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX tasks_project_id_idx ON tasks(project_id);
CREATE INDEX tasks_external_id_idx ON tasks(external_id) WHERE external_id IS NOT NULL;
CREATE INDEX tasks_status_idx ON tasks(status);

-- ============================================================
-- Events (append-only timeline of task state transitions)
-- ============================================================
CREATE TABLE events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  event_type TEXT NOT NULL,         -- 'preflight_proceed' | 'build_started' | 'pr_opened' | 'review_pass' | etc.
  payload JSONB NOT NULL DEFAULT '{}'::jsonb,
  emitted_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  emitted_by TEXT NOT NULL          -- 'forge' | 'mirror' | 'beacon' | 'outbox_notifier' | 'larry' | 'system'
);
CREATE INDEX events_task_id_idx ON events(task_id);
CREATE INDEX events_emitted_at_idx ON events(emitted_at DESC);

-- ============================================================
-- Decisions (project-level decision log; replaces hand-written "decisions locked" markdown)
-- ============================================================
CREATE TABLE decisions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  context TEXT,
  options_considered JSONB NOT NULL DEFAULT '[]'::jsonb,  -- array of {label, pros, cons}
  decision TEXT NOT NULL,
  decided_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  decided_by TEXT NOT NULL,                                -- 'larry' | 'beacon' | 'larry+claude'
  reversibility TEXT NOT NULL DEFAULT 'medium' CHECK (reversibility IN ('easy', 'medium', 'hard'))
);
CREATE INDEX decisions_project_id_idx ON decisions(project_id);

-- ============================================================
-- Triggers: auto-update timestamps on mutation
-- ============================================================
CREATE OR REPLACE FUNCTION touch_last_updated() RETURNS TRIGGER AS $$
BEGIN NEW.last_updated = NOW(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS TRIGGER AS $$
BEGIN NEW.updated_at = NOW(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER projects_last_updated_trigger
  BEFORE UPDATE ON projects FOR EACH ROW
  EXECUTE FUNCTION touch_last_updated();

CREATE TRIGGER programs_updated_at_trigger
  BEFORE UPDATE ON programs FOR EACH ROW
  EXECUTE FUNCTION touch_updated_at();

-- ============================================================
-- RLS: enable on all 5 tables. No policies created (zero access for anon).
-- Service-role bypasses RLS by design.
-- Future migrations add anon policies if client-side queries are introduced.
-- ============================================================
ALTER TABLE programs  ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects  ENABLE ROW LEVEL SECURITY;
ALTER TABLE tasks     ENABLE ROW LEVEL SECURITY;
ALTER TABLE events    ENABLE ROW LEVEL SECURITY;
ALTER TABLE decisions ENABLE ROW LEVEL SECURITY;

-- ============================================================
-- Seed: 6 default Programs (mirror Marvin Mission Control + add Agent OS Development)
-- ============================================================
INSERT INTO programs (name, description, color, position) VALUES
  ('Agent OS Development', 'Building + evolving the agent OS itself (Phase E/F work, infra, healers, agent personality docs)', '#6366F1', 0),
  ('TruPath', 'TruPath workflows and integrations (PII-sensitive, client-facing)', '#10B981', 1),
  ('The Thing', 'Next big holding initiative', '#F59E0B', 2),
  ('AI Company', 'AI services co with Robert Nickell + Nick Ham', '#EC4899', 3),
  ('Marvin System', 'Marvin-the-agent (Openclaw, Mac Mini)', '#3B82F6', 4),
  ('Personal', 'Personal projects and tasks', '#8B5CF6', 5);

-- Migration complete. After supabase db push, verify with:
--   SELECT count(*) FROM programs;  -- expect 6
--   SELECT name FROM programs ORDER BY position;
```

Forge implements this EXACTLY. If anything in the SQL has a Postgres-15 idiom issue or a Supabase-specific consideration (e.g., `gen_random_uuid()` requires pgcrypto extension which Supabase enables by default), Forge handles those nuances + flags via CLARIFY_REQUEST if a real conflict arises.

### 4.4 New file: `supabase/SCHEMA.md`

Hand-written rationale block at top (~150 lines explaining the design choices) + auto-generated table-by-table reference below. Rationale block covers:
- Why 5 tables (not 3, not 10) — references overview spec § 5.1
- Why RLS-enabled + no anon policies — security posture
- Why JSONB on `links`, `payload`, `options_considered` — flex without schema explosion
- Why CASCADE on FKs — Program/Project/Task ownership is strict; you don't orphan
- Why `position` columns everywhere — drag-drop is load-bearing for the kanban UX
- Why `external_id` on tasks — bridges agent OS task naming to PM model
- Why triggers on `last_updated` / `updated_at` — single source of truth for "last modified"
- Why a `decisions` table at all — replaces the hand-written "decisions locked" markdown that scatters across specs

Auto-generated section: pulled from `supabase db dump --schema-only` post-migration. Forge can generate this manually OR include a Makefile target / npm script for re-running it as the schema evolves.

## 6. Out of scope (explicit deferrals)

- **Anon-role RLS policies.** No client-side queries planned in E4. Add policies in a later migration if/when needed.
- **Storage buckets, edge functions, realtime channels.** Not needed for PM.
- **Type generation (`supabase gen types typescript`).** Comes in E4.3 (alongside `pm_writer` and Beacon CLAUDE.md updates) when we have actual queries to type.
- **Multi-environment migrations (dev / staging / prod separation).** Single project + single environment. Branching/preview environments come if multi-tenancy demands.
- **Foreign-key indexes on every FK.** Created indexes are deliberately the ones queries will actually hit. Add more in future migrations if real query patterns reveal slow paths.
- **Audit log table.** Events table is the closest thing; we don't replicate to a separate "audit_log" because Events already serves that purpose for Tasks. If we want Program / Project / Decision-level audit, that's a future migration.
- **Soft-delete on tasks/projects.** Status enum has `cancelled` / `dropped`; hard-delete via CASCADE is fine for v1.

## 7. Architecture decisions locked

| Decision | Value | Rationale |
|---|---|---|
| Table count | 5 (Programs, Projects, Tasks, Events, Decisions) | Matches overview spec § 5.1 exactly. Don't add more in v1. |
| RLS posture | Enabled on all 5; zero anon policies | Service-role-only access for E4. Defense in depth + future-proofing for adding anon policies in later migrations. |
| Primary keys | UUID v4 via `gen_random_uuid()` | Standard Supabase pattern; avoids sequence contention; matches Joe's Sage schema style. |
| Foreign-key delete behavior | CASCADE everywhere | Program → Project → Task ownership is strict. Don't want orphans. |
| JSON-typed columns | JSONB (not JSON) | Indexable + faster than JSON for our access patterns. |
| Position columns | `INTEGER NOT NULL DEFAULT 0` on programs / projects / tasks | Drag-drop reorder is load-bearing for kanban UX. No fractional positions in v1 — accept O(n) on reorder writes; revisit if it bites. |
| `external_id` on tasks | TEXT, nullable, partial index | Maps agent OS task naming (`task-30-...`) to PM rows. Partial index excludes NULLs (human tasks). |
| Timestamp trigger | BEFORE UPDATE on projects (last_updated) + programs (updated_at) | Single source of truth for "modified at." Tasks have explicit started_at + completed_at, no auto-update needed. |
| Seed data | 6 Programs hardcoded in migration | Reproducible, minimal, matches Larry's existing Mission Control state. E4.2 migration script does NOT re-create these; it just adds Projects under existing Program IDs. |
| Postgres version | 15 (Supabase default) | No need to opt into 16 yet. |
| Migration file naming | `0001_*.sql` (4-digit zero-padded) | Standard Supabase CLI convention; sorts correctly forever. |
| `supabase db push` policy | Larry-driven, post-merge, manual | Per locked decision in overview spec § 2. The migration-check workflow gates PRs; the push is a human gate. |

## 9. Risks + rollback

| Risk | Mitigation | Rollback |
|---|---|---|
| SQL has a Postgres-15 syntax issue | Migration-check workflow runs `supabase db lint` on PR; Forge tests locally via `supabase start` in tmpdir if Docker is available. | Forge revises the migration; re-PR. Nothing in prod yet so no data risk. |
| `gen_random_uuid()` requires extension Supabase doesn't enable by default | Supabase enables `pgcrypto` by default since 2024; verify via lint. If lint flags, add `CREATE EXTENSION IF NOT EXISTS pgcrypto;` as first statement. | One-line migration edit + re-PR. |
| RLS enabled but no policies causes some Supabase dashboard / CLI features to error | Test in Supabase dashboard's Table Editor post-push; if any errors arise, those are about admin UI not application code (service-role works regardless). | Add Supabase-internal policies via a separate migration if needed. |
| Larry runs `supabase db push` before reading migration content | The push command prints the migration filename(s) about to apply and asks `Do you want to push these migrations to the remote database?` (y/N). | Larry says N; reviews the migration; re-runs when ready. |
| Migration applied successfully but Larry wants schema changes | `supabase db dump --data-only` first to back up any data; `supabase db reset` wipes; new migration `0002_*.sql` rolls forward. Don't edit `0001_*.sql` post-push. | Migration discipline: forward-only. Issue a `0002_*.sql` reversal migration if the design needs to change. |
| 6 default Programs don't match Larry's actual preferences | Easy to ALTER (`UPDATE programs SET name = ... WHERE name = ...`) post-push, OR include in a `0002_*.sql` follow-up migration. Names are not load-bearing. | Edit migration → re-issue migration (forward-only) OR live-edit via Supabase dashboard. |
| GitHub Actions workflow's `supabase db lint` requires authentication | `--linked false` flag tells lint to run against the local migration file without connecting to a project. No auth needed for lint. | Verified: `--linked false` is the correct CLI flag for un-authenticated lint of SQL files. |
